# 06 · 启动令（给新 AI · 可整段复制）

> 用法：把下面代码块**整段**发给新 AI。它会自己读文档，不需要你再解释背景。

```
【任务】05 · serial-monitor 门外 AI 契约补齐（第一批）

■ 你的任务目录（先全读，按顺序）
e:\linkdesk\docs\05-插件更新\serial-monitor-门外AI契约补齐\
  00-README.md          案由 / 范围 / 判据
  01-现状与证据.md       现状与行号（开工前重新核一遍，代码会漂）
  02-方案与契约.md       做成什么样（回执形状与语义不许悄悄改）
  03-边缘情况清单.md     16+ 例，逐条过
  04-任务清单.md         ← 进度唯一真相源
  05-真机验收.md         六个真机场景
  07-发版与归档.md       发版链与归档步骤

■ 插件仓
E:\linkdesk-plugins\official\serial-monitor
先读它的 AGENTS.md（绿灯只由本仓 verify/test 给）。

■ 背景一句话
两个真实工程的零知识外部 AI 用 CLI/MCP 调试硬件，暴露了串口插件的契约问题。
本批把最痛的四组补上：A 状态可信 / B① 缓冲查询 / C 等待原语 / E 复位。
一次改、一次验、发一个 1.0.37。

■ 铁律（破了就停）
1. 一次改一次验一次发：四组同笔，只发一个 1.0.37，⛔ 不按组拆版本。
2. 壳零改动：⛔ 不碰 e:\linkdesk 的 electron/ 与 src/。
   若发现「必须改壳才能做」⇒ 立刻停下回报，不要就地改。
3. 发版前必须让我看屏裁决，⛔ 不许自作主张发。
4. 真机环：LINKDESK_CDP_PORT=9333 npm run dev:real
   换端口重启前先杀旧 node 实例，否则第二个实例静默失败。
5. 三门全绿才提交：npm run verify（九段）/ npm run test / npm run build。
6. 提交信息用 fix: 或 feat: 直连前缀；推送带代理 127.0.0.1:7890。
7. 单测 fixture 用虚构值（硬约束 21）：不写真实插件 id / 真实 UI 文案。
8. 新命令 meta 必须带 description + params（硬约束 26）。

■ 开工顺序（严格）
第一步只做 T0：读 stream 实现，核实「暂停期间吞数据、恢复后不回放」是否属实。
只给结论：属不属实 + 证据 file:line。⛔ 不要先写代码。
我确认后，再按 04-任务清单 做 A/B①/C/E。

■ 三个「停下来说」的触发点
1. 需要改壳
2. 需要写盘（日志落盘 / 落点登记）
3. 需要改变现有语义（例如把「暂停不回放」改成回放）

■ 做完的定义
- 04-任务清单 全 ✅（含 Q1–Q4 测试与门禁）
- 05-真机验收 六场景由我看屏通过
- 07-发版与归档 走完（发版 + 目录收录 + 归档归还）

■ 本批明确不做
B② 日志落盘 · D 编码「自动」档 · F 便捷项（capture 预设 / exportLog 路径）· 任何壳改动。
```

## 附：为什么这样派

- **先读文档再动手**：四份子档分工清楚（现状/契约/边缘/任务），避免"边写边猜"；
- **T0 前置**：有一条语义（暂停是否回放）**没核实**，先定事实再改码，⛔ 不许顺手改语义；
- **三个停点**：这个任务最容易越界的两处（改壳、写盘）都设了红灯；
- **完成定义写死**：避免"代码写完就算完"，验收与归档都算在任务里。
